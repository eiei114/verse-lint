# V2003 — mixed-line-endings

Opt-in; warning; no safe fix. Purpose: notice a file whose line endings are not
consistent after a merge, a copy-paste or an editor that rewrote part of it. This
is a team policy warning about file consistency, not a compiler or syntax claim.

## Why the tool has to say something

Mixed LF and CRLF inside one file is preserved by design: the tool reads bytes,
reports one-based lines that treat `\r\n` as a single terminator, and writes back
the terminators it found. That is the right behaviour for a read-only linter, but
it also means a file that already mixes styles is accepted silently — and the
next diff, formatter or editor may rewrite every line at once. This rule turns
that silent state into one visible warning.

## Detection

- The check reads **source bytes**, not tokens: a terminator is a byte-level
  property, so a `\r\n` inside a string or a comment counts exactly like one
  between two statements. No token stream or scope graph is consulted.
- The first terminator in the file defines the reference style. A file is
  reported when at least one later terminator is the other style, i.e. it
  contains at least one CRLF **and** at least one bare LF.
- Exactly **one** finding per file, anchored at the first terminator whose kind
  differs from the first one. The range covers that terminator only
  (`\r\n` → two bytes, `\n` → one byte), so it points at the byte to look at
  instead of flooding a large file with one finding per offending line.
- Bare `CR` never reaches this rule: `verse-lint` already refuses a source with a
  `CR` that is not followed by `LF` as an execution error.
- A file must still pass the ordinary parse and coverage validation. A file that
  fails them is an execution error as before and gets **no** V2003 finding, so
  the rule never speaks about a file the run could not analyze.

## What is not reported

- **LF-only** files, which are the project default.
- **CRLF-only** files. A checkout may legitimately be CRLF throughout; that is a
  consistent file, not a mixed one.
- **Empty files**, a BOM-only file, and a **single line without a terminator**.
  There is no terminator to conflict with.
- A **CRLF at the very end** of an otherwise LF file is still mixed: the last
  terminator differs from the first, and it is reported. The exclusion is only
  about a file whose terminators are all one kind.
- Files the run could not analyze, which fail coverage validation instead.

Good: `A := 1\nB := 2\n` and `A := 1\r\nB := 2\r\n` — one style, no finding.
Bad: `A := 1\r\nB := 2\n` — reported at the `\n` terminating line 2.
Bad: `A := 1\nB := 2\r\n` — reported at the `\r\n` terminating line 2.
Counterexamples: `A := 1` (no terminator), an empty file, and a file whose only
terminator is the last CRLF.

## Severity and default

`warning`, and **not** selected by default. Enable it with `--select V2003`, with
the policy prefix `--select V2`, or in `[lint] select`. Once selected, a warning
exits 0 unless `--deny-warnings` is set, or `[lint.severity] V2003 = "error"`
raises its severity. Severity changes never select a rule, so a project that only
sets `[lint.severity]` still gets no V2003 finding.
Everything else comes from the shared rule machinery: `--ignore V2003` /
`[lint] ignore` removes the rule for a project, `--show-config` prints the
effective severity, and JSON/SARIF/GitHub output derive metadata from
`rules::REGISTRY`.

## Suppression

A line directive on the **diagnosed line** suppresses it, because that is the
line the terminator ends:

```text
# verse-lint: disable-next-line V2003 -- imported file, normalised at the source
A := 1
B := 2
```

`disable-line` also works when the same physical line already contains code, and
`--ignore V2003` (or `[lint] ignore = ["V2003"]`) suppresses the whole rule. Like
every other rule, a directive needs a nonempty ` -- reason`.

## No safe fix

Normalising line endings rewrites every line in the file — exactly the
wholesale change this rule warns about — and the tool cannot know which style the
project wants, or whether a mixed file is a deliberate artifact mid-merge. That
decision belongs to a human or a formatter, so this rule is `fixable: false` and
`--fix` never touches it. Normalising is not offered as an option here; the
existing byte-preservation contract for mixed line endings is unchanged.
