# V3003 — variable-shadowing

Opt-in; warning; no safe fix. Purpose: show a local that silently reuses an
outer name, so a reader can see which binding a later edit will capture. This is
a semantic rule built on the [scope graph](../semantic-model.md), not a compiler
rule, and it is not selected by default: a shadowing name is often deliberate,
and the rule is an observation rather than a defect claim.

V3003 reports a binding whose name resolves to another binding in an **ancestor**
scope, when both are lexical declarations this model tracks (`variable`,
`constant`, `parameter`, `forBinding`). Exactly one finding is emitted per
shadowing pair, spanning the **inner binding's name range only**. The message is
the fixed English string `Declaration shadows an outer binding`: the identifier
is already in the reported range, so embedding it would make output less
deterministic and harder to grep. The finding never names the outer binding.

## What is reported

- a local in an inner block whose name is also declared in an enclosing block,
  function body, class body or file scope;
- a local whose name is also a function `parameter` of the enclosing function;
- a `for` iterator binding or `if` condition binding whose name is also a local
  in an enclosing scope.

A `for`/`if` binding that rebinds the **immediate enclosing function's own
parameter** of the same name is not reported. That shape — `for (Param : Param)`
or `if (Param := ...)` inside a function whose parameter is also `Param` — is
idiomatic in Verse iteration, and reporting it would only add noise.

## What is never reported

- **Anything at all, when the graph is incomplete.** If the model recorded any
  construct it could not classify, the file's graph has `is_complete() == false`
  and this rule emits nothing — no diagnostic and no execution error — under
  every configuration. A shadowing claim from a graph that could not see every
  name is not evidence about what the inner name captured.
- **Two bindings in the same scope.** Two declarations of one name in one scope
  are a *redeclaration*, which Verse's own rules govern. That is a different
  question with different authority, so this model does not invent a second
  diagnostic for one line.
- **A type, class, enum, struct, interface, function name or module import as
  the outer binding.** Shadowing a type name with a local is a real hazard, but
  this model has no namespaces yet: it cannot tell a value name from a type name
  when both are spelled the same. Claiming that pair today would produce false
  positives on legitimate code, so type-versus-value shadowing is deliberately
  left out of this slice.
- **An outer declaration that appears later in the source.** A binding only
  captures a name once its declaration starts, matching the resolution rule in
  [the semantic model](../semantic-model.md): a name declared after the inner
  declaration never captured anything.
- **A `_`-prefixed inner name**, the conventional "deliberately unused" marker,
  and any name listed in `[lint] shadow-allow`.
- **An ancestor that is not the nearest one.** A name that shadows two ancestors
  yields one finding for the nearest pair, because the outer side appears in no
  part of the finding and the nearest ancestor is the only one the model could
  name.

## Parameters

`[lint] shadow-allow` is a list of exact, case-sensitive identifiers, empty by
default. A project with a deliberate naming convention can keep it while the
rule stays on:

```toml
[lint]
select = ["V3003"]
shadow-allow = ["Index", "Slot"]
```

The entries only silence matching shadowing findings; they do not create
bindings, rename anything or affect other rules. Empty entries are rejected.
`--show-config` prints the resolved list.

## Selecting it

The rule is off by default. Enable it with `--select V3003`, with the semantic
family prefix `--select V3`, or with the whole registry through `--select V`.
Everything else is inherited from the shared rule machinery and is not
special-cased here: `[lint.severity]` may promote it to `error`, `--ignore
V3003` removes it, a `verse-lint: disable-next-line V3003 -- reason` directive
on the inner declaration's line suppresses it, and `--show-suppressed` lists it
again. A warning exits 0 unless `--deny-warnings` is set.

## No safe fix

There is none, by design. Renaming or removing a binding is a semantic change a
human has to judge, and the rule deliberately suggests no rename. It is
`fixable: false` in the registry, so `--fix` never touches it.
