# V1005 — excess-final-blank-lines

Opt-in; warning; **no safe fix**. Purpose: catch a file that ends with blank
lines left behind by an editor or a merge. These lines survive every other rule
— V1001 flags whitespace *on* a line, not an empty line, and V1002 only objects
to a missing terminator — yet they produce noisy diffs and hide which line the
content really ends on. This is a trivia-only file policy, not a compiler claim.

## Detection

The check reads the token stream, not the bytes. Everything between the last
token that is neither trivia nor a comment and the end of the file is
terminators and, at most, whitespace, so a terminator inside a string, a
character literal or a comment can never be mistaken for one of these lines.

- A **nonempty body** ends cleanly when it has exactly one final terminator
(`\n` or `\r\n`). That is the file termination V1002 asks for.
- Two or more terminators after the last content token mean at least one blank
  line, and the file is reported.
- Exactly **one** finding per file, and the range runs from the first byte of the
  first blank line to end of file. A tail of fifty blank lines therefore costs one
  warning whose extent is visible, not fifty of them — the same one-finding-per-
  file stance [V2003](v2003.md) takes for mixed endings.
- The check runs only for a file the ordinary parse and coverage validation
  accepted. An unanalysable file stays an execution error with exit 2 and gets
  **no** V1005 finding.

Bad: `A := 1\n\n` — one blank line, reported at line 2.
Bad: `A := 1\n\n\n\n` — three blank lines, still one finding.
Good: `A := 1\n` and `A := 1\r\n` — one terminator.
Good: `A := 1\n# note\n` — a final comment line is content, and one terminator
after it is clean.

## What is not reported

- **Empty, BOM-only and whitespace-only files.** There is no content to end, so
  nothing is excess. A whitespace-only body without a final newline is
  [V1002](v1002.md)'s finding, and the spaces themselves are
  [V1001](v1001.md)'s.
- **A whitespace-only trailing line**, such as `A := 1\n  \n` or
  `A := 1\n\n  \n`. That line is V1001's finding; this rule counts only
  genuinely empty lines, so no line is ever described by both rules.
- **Blank lines inside a block comment or a string**, because those terminators
  belong to the protected token. `<# x` / blank / `y #>` is untouched, and a
  following real blank line is reported where it is.
- Files the run could not analyze, which fail coverage validation instead.

## Severity and default

`warning`, and **not** selected by default. Enable it with `--select V1005`, with
the `--select V1` or `--select V` families, or in `[lint] select`. Once selected,
a warning exits 0 unless `--deny-warnings` is set, or `[lint.severity]
V1005 = "error"` raises its severity. Severity never selects a rule, so a project
that only sets `[lint.severity]` still gets no V1005 finding.

Everything else comes from the shared rule machinery: `--ignore V1005` /
`[lint] ignore` removes the rule for a project, `--show-config` prints the
effective severity, and JSON/SARIF/GitHub output derive metadata from
`rules::REGISTRY`, where SARIF `defaultConfiguration.enabled` is `false`.

## No safe fix

Removing trailing blank lines rewrites bytes outside any finding the author
marked, and the tool cannot know whether the tail belongs to the file or was
about to be typed into it. That decision is a human or formatter edit, so this
rule is `fixable: false`, `--fix` never touches it, and `--fix --diff` prints no
diff for it. A later slice may add one once the rule is proven; this one does not.

## Suppression

This is a **file-level** rule like V1002: a line directive cannot name it.
`# verse-lint: disable-line V1005 -- reason` and `disable-next-line` both fail with
exit 2 and the message `file-level V1005 cannot be suppressed by a line
directive; use config ignore`, whether or not V1005 is selected. Use
`--ignore V1005` or `[lint] ignore = ["V1005"]` when a project intentionally
keeps a trailing blank line.
